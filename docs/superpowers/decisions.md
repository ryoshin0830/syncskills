# Decisions made while building oneset

Every judgement call taken during implementation, with why it was taken and what
it costs if it turns out wrong. Kept because the reasoning is worth more than the
outcome: most of these were forced by something the plan had got wrong.

## Rulings (pre-flight)

Ruling 1 (finding 2): `mergeFile` treats exit 255 as failure and 1..127 as "conflicts present". Rationale: that is git merge-file's documented contract; `< 0` is unreachable. Cost if wrong: a genuine merge-file crash is mistaken for a conflict and escalates to the agent, which then fails validation — noisy, not silent.

Ruling 2 (finding 3): add `payload?: unknown` to `Side` in `src/core/types.ts`. Rationale: the field is already load-bearing in two tasks; typing it is smaller than rerouting the data. It is excluded from hashing and from equality, so it cannot affect a decision. Cost if wrong: a slightly wider type than needed.

Ruling 3 (finding 8): `createGitStore` takes `remoteOverride?: string`, and `EngineOptions` gains `remoteOverride?: string` passed straight through. Rationale: without it the two-device suite — the test that proves the product — cannot run offline. Cost if wrong: one extra optional field on a config object.

Ruling 4 (finding 9): delete the post-push `upsertEntry` loop from `runSync`. Order becomes applyPlan (which upserts) → writeManifest → commitAndPush → secrets.write → saveState. Rationale: `saveState` must come last so an interrupted run re-resolves safely, per the spec's §6.1 invariant. Cost if wrong: manifest entries lag one sync behind; caught by the idempotency test in Task 14.

Ruling 5 (finding 10): Task 12's implementer writes `src/dispatch.ts` in full, to this contract — a `dispatch(args, json)` that loads config, returns EXIT.UNINITIALIZED when `loadConfig` is null (except for `init`, `doctor`, `config`, `completion`, `help`), maps command → module, and derives the exit code as: failed ⇒ ERROR, unresolved or pending ⇒ CONFLICT, else OK. Cost if wrong: the smoke test in Task 15 catches a wrong code.

Ruling 6 (finding 11): drop `guard()`; instead scan the staged text of every pushed skill file with `scanForSecrets` before commit, and fail the push naming the file. Rationale: the spec requires an independent pre-push scan (§5) and a no-op satisfies neither the spec nor the rubric. Cost if wrong: a false positive blocks a push; the message names the file so it is diagnosable.

Ruling 7 (finding 12): `Device` is whatever the Task 14 tests call. The implementer owns its shape; `breakCcSwitch()` makes the stub cc-switch binary exit non-zero. Cost if wrong: helper churn inside the test suite only.

Ruling 8 (findings 13,14,15): fixed in passing by the owning task's implementer; not tracked as findings.

Ruling 25 (found by the integration suite): `manifest.generatedAt` was stamped on every write, so a sync with zero changes still produced a commit — defeating the deterministic serialization that exists precisely to avoid history noise. Decision: remove generatedAt entirely; the manifest is now a pure function of its entries, and each entry already carries its own updatedAt. Cost if wrong: no record of when the manifest file itself was last written, which git already provides.
Second review round: 8 findings, all reproduced against the built `dist/cli.js` before any code changed, and each one given a test that failed first.
Ruling 26 (corrects the review itself): the review asked for `saveState` to move before `commitAndPush`, or to run on failure. That is WRONG and the original ordering was right. A `push-content` action records base = local content; if the push never landed, the next run sees base == local with the item absent from the remote, which `decide()` reads as DELETE_LOCAL — it would delete the user's skill. Decision: keep the ordering, and fix the real half of the problem instead. `saveBaseTree` has already written the base TREES by then, so a rejected push leaves a tree that `state.json` does not describe; those trees are now dropped (`dropWrittenBases`), and the TUI additionally refuses any base tree without a matching state entry before using it as a merge ancestor. Cost if wrong: a rejected push discards base trees that a later run recomputes from `recordAgreedBases` anyway.
Ruling 27: a rejected push is NOT retried with fetch+rebase, even though that was the review's first suggestion. Every sync rewrites `manifest.json`, so the replay would conflict on essentially every race and the recovery would be less predictable than the failure. Decision: `PushRejected` is a typed outcome, `runSync` reports it instead of throwing, and because the run's state was never saved, simply running again rebuilds the whole decision against the store as it now stands. That is the retry, one process later, with the resolver doing the merging rather than git. Cost if wrong: a busy pair of machines needs a second invocation; the integration suite proves the second one converges.
Ruling 28 (the class the review found twice): `Buffer#toString('utf8')` does not fail on invalid bytes, it substitutes U+FFFD — so decoding two different binaries yields the SAME string and `mergeTrees` called them identical, dropping one side with `resolved: true`. Decision: every comparison in mergeTrees is over bytes now, and a binary both sides moved is reported `unresolved` rather than merged. This is the same non-injective-encoding trap `canonicalize()` already refuses to fall into; the comment there now has a sibling.
Ruling 29: `writeFile` creates 0644, and `treeHash` hashes the executable bit — so a merged `run.sh` propagated as non-executable to every machine, including on the plain `git merge-file` path with no agent involved. Decision: `inheritMode` after every write in mergeTrees. The invariant to hold going forward is that anything included in `treeHash` has to survive every write path, not just `copyFile`.
Ruling 30: the `p.isCancel` fix from the first round landed in `init` only, and the TUI still read `go !== true` — where a cancel symbol takes the "declined" branch and calls `publish()`, so Ctrl-C pushed to git and exited 0. Decision: one shared `src/prompt.ts` (`answer`, `required`, `Cancelled`), used by both, plus `EXIT.CANCELLED = 130`. No prompt result is compared against a literal anywhere now, which is what made the bug possible.
Ruling 31: refusing unknown flags created a second, quieter gap — a flag that exists but does nothing for this command. `sync --merge-agent codex` exited 0 while `sync --help` says in so many words that sync does not merge. Decision: `src/flags.ts` holds `FLAGS_FOR` per command alongside `parseOnly`/`parseAgent`, and validation moved up into `main()` so it runs BEFORE the non-TTY branch that prints help and exits 0 — otherwise `oneset --no-tui --merge-agent claud` still reported success. `parseAgent` now throws on an unknown name like `parseOnly` does, instead of substituting `auto`.
Ruling 32: `delete-local` removed a skill's directory but not its cc-switch row, leaving a row `localSkillSides` skips forever and `unmanagedSkills` does not see (it looks the other way). Decision: `CcWriter.deleteSkill`, symmetric with `deleteMcp`, going through the database under the same running-cc-switch guard as the other direct writes; the directory is left alone when the row cannot go, because half a deleted skill is worse than a delayed one.
